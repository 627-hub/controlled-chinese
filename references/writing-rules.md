# 受控中文规则参考

本文件定义 v0.1 的写作规则与检查边界。示例只说明结构，不替作者判断真实语义。

## CC-001：单句单指令

**要求**：一个句子只要求读者执行一个动作。将“读取、解析并返回”等连续动作拆成有序步骤。

- 反例：`读取配置并校验字段，然后启动服务。`
- 正例：`1. 读取配置。2. 校验配置字段。3. 启动服务。`

**例外**：一个不可拆分的原子操作不拆，例如“保存并关闭对话框”若只是同一个界面按钮的名称，应保留按钮名称。并列说明不代表连续指令时，不机械拆分。

## CC-002：条件与例外范围

**要求**：明确条件作用于全部动作还是部分动作，明确例外针对哪个对象。

- 反例：`如果文件不存在或已损坏，删除缓存并重试。`
- 正例：`如果文件不存在或文件已损坏，先删除缓存，再重试操作。`（仍需按 CC-001 拆成两个步骤。）
- 更明确：`如果文件不存在或文件已损坏：1. 删除缓存。2. 重试操作。`

不要移动条件后改变原意。不能确定条件范围时，请求确认。

## CC-003：行为者明确

**要求**：当步骤可能由不同主体执行时，写明行为者。

- 反例：`管理员提交申请后，审批并发送通知。`
- 正例：`管理员提交申请。审核员审批申请。审核员发送审批结果通知。`

中文命令句可以省略“你”或默认操作者；不要给每个命令句机械补主语。只有行为者发生切换或无法唯一确定时才补出。

## CC-004：跨句省略

**要求**：后句省略的主语或宾语存在多个候选对象时，重复必要名称。

- 反例：`拆下盖板。检查有无裂纹。`
- 正例：`拆下盖板。检查盖板有无裂纹。`

上下文只有一个合理对象且文本简短时，允许自然省略。不要为了形式完整而重复所有名词。

## CC-005：指代明确

**要求**：指代词只能指向一个明确对象。

- 反例：`将配置写入缓存和数据库，然后删除它。`
- 正例（原意为删除缓存）：`将配置写入缓存和数据库。删除缓存中的配置。`

“该、此、其”本身并不违规。只有一个先行项时保留；出现多个候选对象时换成全称。不要使用“前者、后者”跨越多个句子维持引用。

## CC-006：并列与逻辑连接

**要求**：消除“和、或、及、以及”造成的层级和范围歧义。

- 反例：`检查传感器和控制器的连接。`
- 正例（检查两处连接）：`检查传感器连接。检查控制器连接。`
- 正例（检查控制器与传感器之间的连接）：`检查传感器与控制器之间的连接。`

“或”表示同时允许两个条件还是只允许其一，无法确定时不要擅自改成“异或”或“至少一个”。

## CC-007：修饰与语义指向

**要求**：多重“的”字结构、长定语或动作指向存在多种解释时，显式重写关系。

- 反例：`解析测试环境的服务日志的格式。`
- 正例：`解析测试环境中服务日志的格式。`
- 反例：`完成任务的检查。`
- 正例（任务已完成）：`检查已完成的任务。`
- 正例（检查动作已完成）：`已完成任务检查。`

不要只以“的”字数量判错；关系清楚的长名词短语可以保留。

## CC-008：否定范围

**要求**：区分全部否定与部分否定，明确否定词管辖的对象。

- 反例：`所有任务都不要重试。`
- 正例（全部禁止）：`任何任务都不得重试。`
- 正例（部分任务）：`并非所有任务都需要重试。`

“不是所有”与“所有都不”不可互换。“未全部完成”也不等于“全部未完成”。

## CC-009：数量与时间端点

**要求**：端点含义影响行为时，用明确范围表达。

- 反例：`超时 30 秒以上的任务会终止。`
- 正例（包含 30 秒）：`超时时间 ≥ 30 秒时，系统终止任务。`
- 正例（不包含 30 秒）：`超时时间 > 30 秒时，系统终止任务。`

不要默认“以上、以下、之前、之后”包含或不包含端点。原文无法确定时，请求确认，不要自行选择 `>` 或 `≥`。

## CC-010：术语一致

**要求**：一个概念使用一个名称；保留必要领域术语，并在首次出现时定义不常见术语。

- 反例：`创建任务后，系统返回作业编号。`（任务与作业原意相同。）
- 正例：`创建任务。系统返回任务编号。`

不要统一本来不同的概念，例如“智能体”和“代理服务器”。项目术语表优先于通用偏好；不要凭语感合并近义词。

## CC-011：步骤与条件列表

**要求**：三个以上连续步骤、多个并列条件或复杂分支优先使用列表。

- 反例：`输入名称、选择环境、设置超时时间。`
- 正例：`1. 输入名称。2. 选择环境。3. 设置超时时间。`

列表不得改变顺序或把“或”条件改成“且”。解释性文字中的简单三项列举不必机械改列表。

## CC-012：信息保真

**要求**：改写前后逐项核对事实与逻辑，不以更短、更肯定或更流畅为目标改变内容。

- `请求可能已失败。`不得改成`请求已失败。`
- `任务尚未完成。`不得改成`任务失败。`
- `仅管理员可以删除日志。`不得删掉“仅”。
- `服务通常会在 5 秒内响应。`不得删掉“通常”。

原文信息不足时，不用常识补齐。原文本身清楚时，不修改。

## 检查器规则

`zh-lint.py` 只做高置信的字符串与结构提示。代码块、行内代码和 URL 会被跳过。
Markdown 表格、引用块、四空格缩进块、时间戳／日志行、裸 JSON 行也跳过；逐行规则只检查含中日韩字符的行，纯英文文本不产生命中。

| 规则名 | 默认级别 | 检查内容 | 不能证明什么 |
|---|---|---|---|
| `mixed-brackets` | error | 中文左括号配英文右括号，或反向混配 | 括号语义是否正确 |
| `ascii-comma` | error | 两个汉字之间使用 ASCII 逗号 | 所有中英混排问题 |
| `duplicate-punctuation` | error | 连续重复的中文句读符号 | 是否有意使用特殊排版 |
| `multi-action` | warning | 中文散文里用分号连接多个信息单元（强信号） | 是否真的包含多个指令 |
| `multi-action-soft` | warning | “，然后／接着／随后／同时”连接动作（弱信号） | 是否只是叙述顺序 |
| `negation-scope` | warning | “所有／全部……都不……”等高风险结构 | 原句在现实语境中是否仍有歧义 |
| `quantity-range` | warning | 数字附近出现“以上／以下／以内／以外” | 是否包含端点 |
| `pronoun-reference` | warning | 前句含并列对象，后句以部分指代词开头 | 指代的真实先行项 |
| `terminology` | warning | 用户术语表中的非批准词形同义词混用 | 未配置术语是否一致 |

## 检查档位

同一个检查器在不同体裁上的噪音差异很大：报告里的分号多是并列数据，规范里的分号才是多个要求。

| profile | 适用 | `multi-action` | `multi-action-soft` | 每行最多一条 |
|---|---|---|---|---|
| `chat` | 聊天、复盘叙述 | 关 | 关 | — |
| `doc`（默认） | 长文、报告 | 开 | 关 | 是 |
| `spec` | 规范、步骤清单 | 开 | 开 | 否 |

```bash
python3 scripts/zh-lint.py chat.md --profile chat
python3 scripts/zh-lint.py spec.md --profile spec
```

`--disable` 在 profile 之上再关闭规则，例如 `--profile doc --disable quantity-range`。

`error` 只表示机械规则命中，不代表语义错误。`warning` 永远需要人工或模型复核。退出码只受 `error` 和 `--baseline` 影响。

## 术语表格式

使用 JSON 对象：键为批准术语，值为需要提示的变体数组。

```json
{
  "登录": ["登陆"],
  "任务": ["作业"]
}
```

运行：

```bash
python3 scripts/zh-lint.py document.md --glossary terms.json
```

只有项目已确认两个词形表示同一概念时，才将它们放入同一组。不要内置通用近义词表。

## 设计依据与边界

规则设计参考以下资源所代表的原则，但不复制其标准文本，也不据此声称合规：

- ISO 24495-1:2023：相关、可查找、可理解、可使用的简明语言原则。
- GB/T 1.1-2020：技术文件的一条一个意思、量值和表述形式要求。
- GB/T 15834-2011：中文标点使用边界。
- GB/T 10112-2019：术语一致与术语工作方法。
- Microsoft 简体中文本地化风格指南：可机械检查的中英混排与格式习惯。
- 中文零指代、施受关系、修饰范围和结构切分研究：中文特有助读难点的来源。

v0.1 是面向 agent 文本的写作与改写辅助骨架，不是通用中文标准、翻译规范或航空维修文档规范。
